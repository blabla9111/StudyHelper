# StudyHelper — инструкции для ИИ-агентов

## Что это
Концепт «цифрового деканата будущего» для конкурса: личный кабинет студента, преподавателя и сотрудника деканата. Вуз вымышленный («Университет „Северный берег“»). Автор проекта работает одна, нетехнический пользователь Windows, поэтому всё должно запускаться командами `npm install` и `npm run dev`.

## Стек
Next.js 16 (App Router) + React 19 + TypeScript (strict), Tailwind CSS 4, SQLite через better-sqlite3, bcryptjs для паролей, иконки lucide-react, шрифт @fontsource-variable/inter. Без внешних сетевых запросов при работе (сайт открывается из России без VPN).

## Структура
- `src/app/(app)/` — страницы кабинета (требуют входа, layout вызывает `requireUser`)
- `src/app/login/` — вход
- `src/app/api/` — API: вход, выход, уведомления
- `src/components/` — интерфейс; `AppShell` — меню, шапка, колокольчик
- `src/lib/` — база (`db.ts`, `schema.ts`), сессии (`auth.ts`), роли и меню (`nav.ts`), форматирование
- `src/lib/messages.ts` — все правила сообщений (кто кому может писать, диалоги, рассылка); `src/components/messages/` — интерфейс раздела; `src/app/api/messages/` — API
- `scripts/seed.ts` — вымышленные данные; `scripts/check-security.mjs` — автопроверка защиты

## Жёсткие правила
1. **Только вымышленные данные.** Никаких настоящих ФИО, оценок, номеров зачёток, логотипов и названий вуза.
2. **Безопасность:** данные выбираются по id из сессии, не из адреса и не из тела запроса; у каждого запроса к чужим данным проверка владельца на сервере; пароли только как bcrypt-хеш; ключи и пароли сервисов только в переменных окружения; POST-запросы проходят проверку Origin.
3. **Роли:** student, teacher, staff. Преподаватель правит только свои ведомости; студент видит только свои оценки, заявки, уведомления; одногруппникам показывается только ФИО.
4. **Мобильная версия — основная.** Всё должно работать на ширине 360 px без горизонтальной прокрутки, кнопки не меньше 44 px, поля ввода 16 px.
5. **Интерфейс на русском.** Продумывать пустые состояния, загрузку и ошибки в каждом разделе.
6. На сайте всегда видна плашка «концепт для конкурса, не официальный сервис вуза».
7. Только библиотеки, шрифты и иконки с разрешающей лицензией.

## Проверка перед сдачей работы
`npm run typecheck`, `npm run build`, запуск `npm start`, `npm run check:security`, `npm run check:flows`, `npm run check:features` и `npm run check:messages` (после каждой изменяющей проверки `npm run seed`; для повторного `check:messages` перезапустить сайт, лимиты хранятся в памяти), скриншоты на 360 px и на компьютере. Новые правила доступа добавлять в `scripts/check-security.mjs`.

## Сообщения: правила, которые нельзя ломать
- Кто кому пишет первым: студент → свои преподаватели и одногруппники; преподаватель → студенты своих групп, любые преподаватели и деканат; деканат → любые студенты и преподаватели. Студент отвечает деканату в существующем диалоге.
- Права проверяются только в `src/lib/messages.ts` (`canInitiate`, `canWriteTo`, `getConversationForUser`). Чат группы: только роль student и своя группа; преподаватель и деканат не участвуют.
- Ответ на запрещённую пару и на несуществующего пользователя одинаковый (404). Текст сообщений всегда выводится как обычный текст, без `dangerouslySetInnerHTML` и без превращения ссылок в кликабельные.
- Получателей рассылки сервер определяет сам по группам преподавателя; клиент присылает только id групп.
- SQLite `LOWER()` не понимает кириллицу: поиск по именам делается в коде.

## Заявки, запросы на запись, расписание
- Заявка в «Архиве» студента: статус ready/rejected и `updated_at` старше месяца (`isArchivedRequest` в `src/lib/request-catalog.ts`). Любая смена статуса обновляет `updated_at`.
- Запросы на запись одной пары (`lesson_id` + `date`) показываются одной карточкой-таблицей; ответ всем идёт через `/api/recording-requests/answer` (`lessonId`+`date`, по умолчанию только ожидающим, `all: true` для всех) или одному (`id`). Уведомление преподавателю одно на пару, адрес `/recordings#pair-<lessonId>-<date>`.
- На странице расписания не показывать список сегодняшних пар: он на главной.

## Интерфейс и API: правила после аудита
- Подписи оценок и типов контроля только из `src/lib/labels.ts` (компонент `Short`), полную форму не писать в таблицах.
- Новый файл `route.ts` в `src/app/api` дополнять заглушками `notAllowed` для остальных методов (см. любой существующий маршрут), чтобы ответ был JSON.
- Статус заявки двигает только staff (`/api/requests/status`). Кнопок «ускорить» для студента нет.
- Таблицы, которые на узком экране становятся карточками, переключать контейнерным запросом (`@container` + `@4xl:`), а не `md:`.
- Цвет серого текста не светлее `slate-500` из темы (она уже затемнена), размер текста не меньше `text-xs`; белый текст только на фонах не светлее `emerald-700`, `rose-600`.
- Уведомления удаляются пометкой `dismissed_at`, а не физически; все запросы к `notifications` должны учитывать `dismissed_at IS NULL`.
- Адрес клиента брать только через `clientIp()` (`src/lib/origin.ts`), Origin сверять через `sameOrigin()`; заголовкам `X-Forwarded-*` напрямую не доверять.
- Новое изменяющее действие, которое дорого или создаёт записи, обернуть в `limitUser(userId, "имя", 30)`; тело читать через `readJson` (потолок 64 КБ).
- Справочники по ключу из запроса проверять через `Object.hasOwn`, не через `in`.
- Правки ведомости после открытия пишутся в `audit_log` (`src/lib/audit.ts`); скрипты `seed` и `check:*` не запускать на боевой базе.
- Проверять `npm run check:*` и браузерные сценарии на 360, 390, 412, 768 и 1280 px при шрифте 150%.
